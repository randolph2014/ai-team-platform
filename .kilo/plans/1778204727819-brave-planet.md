## 执行流程（每个迭代）

所有子代理均使用 `Task tool` 的 `subagent_type="general"` 模式，在 prompt 中注入对应代理的指令文件内容。

```
Step 1: 影响面分析
  → Task tool, subagent_type="general"
  → prompt: 读取 /Users/wurui/.claude/agents/impact-analyzer.md 指令 + 迭代目标/任务/验收标准
  → 输出: Impact Analysis Report（Changed Components, Affected Call Chains, Downstream Impact, Edge Cases）

Step 2: 代码实现
  → Task tool, subagent_type="general"
  → prompt: 读取 /Users/wurui/.claude/agents/developer-implementer.md 指令 + 影响面清单 + 迭代任务/验收标准
  → 输出: Changed Files, Validation, Compatibility/Risk, Handoff

Step 3: 代码审查
  → Task tool, subagent_type="general"
  → prompt: 读取 /Users/wurui/.claude/agents/code-reviewer.md 指令 + Step 2 的变更 + 验收标准
  → 输出: Findings (Critical/High/Medium/Low), Release Gate (BLOCKED/CONDITIONAL/PASS)

Step 4: QA 验证
  → Task tool, subagent_type="general"
  → prompt: 读取 /Users/wurui/.claude/agents/qa-tester.md 指令 + 验收标准 + Step 2 的变更清单
  → 输出: Test Matrix, Defects, Release Recommendation (Go/No-Go)

Step 5: 修复 & 合入
  → 如有审查/测试问题（Release Gate = BLOCKED 或 No-Go），回到 Step 2 修复
  → 全部通过后标记迭代完成，进入下一个迭代
```

## 风险与注意事项

1. **迭代依赖**：迭代 5（持久化）和迭代 6（migration）必须在迭代 9（RQ Worker）之前完成
2. **迭代 4（Project 模型）** 可与迭代 7-10 并行，但建议在迭代 5-6 之后
3. **前端迭代 11** 可与后端迭代 9-10 并行
4. **每个迭代的测试必须独立**，不依赖其他迭代的未完成代码
5. **数据库迁移**需谨慎，每个迭代的 migration 文件编号不能冲突
